## 研究记录：有必要才保存

一次性查阅、简单问答或已有文档足以承载的结论，不必创建研究文件。
需要跨会话恢复、比较方案或保存影响决策的证据时，再在当前项目保存记录。沿用现有目录；无约定时可用 `docs/tmp/YYYY-MM-DD_topic.md`，不分配 PRD/ADR/GD 编号。
“临时”表示尚未成为现行规则，不表示证据可以随意丢弃；长期被引用的证据应迁入项目稳定的证据位置。

记录只需回答四件事，可用短段落或小表，不强制独立模板文件：

1. **问题**：这次要确认什么，什么范围内的回答才有效。
2. **证据**：来源或可追溯位置；影响结论时注明版本、环境、日期与方法。
3. **判断**：已证实的事实、推断、未验证内容及结论边界；不能把建议写成批准结果。
4. **去向**：尚未采纳、已吸收到哪份文档、已否定或保留供参考；有真实任务则链接台账，不在研究记录维护执行进度。

正式需求文档也可能处于 Draft；不要求所有 PRD/ADR 草稿搬进临时目录。研究证据与拟议需求/决策按用途区分。

## 被采纳后怎样处理

先把已确认的需求规则、技术决策或操作方法分别写入现有 PRD、ADR、GD，保留关键依据与证据链接。不要只把研究文件移进正式目录就视为完成沉淀。
只采纳其中一部分时，标明已采纳结论的去向与剩余问题，不把整份研究宣称为现行依据。
原记录有追溯价值则保留并注明角色；只有讨论过程而无独立价值的内容可按项目约定精简。原始证据不因结论被采纳而自动变成可删除材料。

## 归档：处理失效依据，不按日期清仓

文档被替代、合并、路线废弃，或不再作为当前参考时归档。已完成但仍定义有效规则的 PRD、仍在使用的 ADR/GD 可以继续保留。
不能仅凭“很久没更新”或“任务全勾选”判断过期；先核对有效内容和实际完成条件。文档与实现冲突时先判断目标行为和实际行为的差异，不能直接归档文档来掩盖实现缺陷。

归档时执行一个短闭环：

1. 将仍有效的规则、未完成事项与必要证据安置到明确去向，避免移动后丢失。
2. 按项目已有结构归档；无约定可用 `docs/archive/YYYY/<原分类>/`。台账仍在自己的归档体系，不混入正式知识目录。
3. 保留编号与原名，在顶部简注原因和当前入口；没有替代文档时如实说明“不再适用，无替代文档”，不虚构链接。
4. 更新当前入口和需要继续可达的引用；检查归档文档自身的相对链接、图片和附件。历史原文中的旧规则保留其历史身份，不能因为修链接而改写决策历史。

说明示例：`Archived: 旧方案已被替代，当前依据见对应 ADR 链接；仅供回溯。` 正式使用时填入可访问的实际链接。
不额外建立需要手工同步的归档状态表；项目已有索引则更新必要入口。

## 历史版本与重复文档

通常由 Git 保存同一文档的修订历史，不每次修改都复制一份快照。
确需保留独立历史快照时，明确原文档、版本日期或提交、快照身份与当前入口。它是同一编号的历史版本，不是另一份同编号的正式文档；查重时区分版本快照与编号冲突。
归档不等于删除；本提案不要求批量清理旧文件，也不自动迁移已有编号。

## 本轮建议与后续

建议仅补充按需读取的研究/归档规则，不新增正式文档类型、强制研究模板或归档模板。主入口保留生命周期原则，具体操作在需要时读取。
确认后，模板讨论即可收尾。接下来应验证实际行为：小改动能否保持轻量、任务能否从表中接续、历史资料是否会被误用、不同目录结构能否适配。验证材料保存在技能仓库维护区，不装进默认运行上下文。

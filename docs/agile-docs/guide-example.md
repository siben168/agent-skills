# GD-001: 更新售后联系资料

状态：虚构草稿，仅示范操作指南写法；未在真实项目执行或验证。
更新：2026-11-09
关联：[PRD-002 统一售后入口](../../skills/agile-docs/references/examples/prd-standard.md)。本文假设项目已有统一联系配置与预览/发布流程，真实使用时应补其实际入口，不能直接视为已核实的 Runbook。

## 用途与适用范围

更换售后页面使用的邮箱、联系账号或二维码，确保现有入口读取一致的信息。
只调整联系资料，不改变登录展示规则或增加新渠道；业务规则以关联 PRD 为准。

## 前置条件

- 已明确本次修改的是哪个站点及环境，拥有该目标的配置维护权限。
- 已获得资料提供者确认的新联系方式与原始二维码，知道哪些字段需要更换。
- 已找到项目统一联系配置及其生效方式；不能假定修改后立即刷新，也不能猜测发布命令。
- 保留此次修改前的资料版本，确认旧联系方式是否仍有效。若已失效，就不能将恢复旧值作为可靠回退。

## 操作与验证

1. 核对目标站点、配置入口与当前有效资料，按需保存可追溯的旧版本。
   - 预期：能区分此次改动值与其他站点的配置；无法确定目标时先停止修改。
2. 在统一联系配置中更新本次字段与图片引用，不逐页复制修改；二维码使用已确认原图。
   - 预期：配置中没有测试资料，图片引用可用；相关入口仍使用同一来源。
3. 按项目已有预览流程查看受影响页面，检查未登录、身份加载中、已登录和手机布局。
   - 预期：公开邮箱可用；登录后资料符合 PRD 的展示规则，图片比例正确，复制内容与页面文字一致。二维码需核对其目标，不只检查图片能否加载。
4. 在本次任务已授权发布的范围内，按既有流程让目标环境生效；否则保留预览并交接。
   - 预期：发布后实际目标页面使用新资料，各引用入口一致；只完成预览时明确标为未发布。

最终结果应能让用户取得已确认的联系方式。页面可访问或构建通过本身不足以证明资料正确，也不证明对方已接受联系请求。

## 失败处理与恢复

| 症状 | 检查与处理 | 何时可以继续 |
|---|---|---|
| 二维码无法加载或指向错误 | 核对原图与引用，获取正确图片；不临时制作未经确认的替代码 | 预览验证目标与显示均正确 |
| 页面仍显示旧资料 | 核对站点、发布版本及配置生效方式，排除检查了错误环境 | 确认修改目标与实际生效版本一致 |
| 上线后发现资料错误 | 若旧资料仍有效，按既有配置/资源发布流程恢复已保留版本；否则使用产品已有的缺项展示策略，保留有效邮箱并等待正确资料 | 实际页面重新通过联系方式与展示检查 |

恢复配置不会撤销用户已经复制、保存或使用过的旧资料。具体一次变更的执行结果和证据写入操作记录，不向本指南追加发布日志。

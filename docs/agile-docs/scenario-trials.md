## 2026-11-10：仓库改名与服务退役后的入口维护

- 技能基线：3531916。
- 方式：当前 Codex 会话手工加载技能，在同步后的真实项目中执行，改动放独立工作树。不是独立盲测；未验证自动发现或其他工具。
- 场景：项目已改名部分仓库、退役部分服务；检查新人入口，修正过时名称、状态与部署手册引用。
- 产出：更新原 README 与关联编辑器任务说明，共两个文件；没有新增 PRD、ADR、任务台账或正式指南，没有改变运行命令。

| 观察点 | 实际结果 |
|---|---|
| 按当前证据判断 | 先同步版本，再交叉核对仓库映射、配置、退役记录和归档替代关系 |
| 投入与规模相称 | 对说明性修正直接更新原文，未机械填充模板 |
| 避免名称误替换 | 区分源码仓库名称与继续有效的运行时服务组、应用和容器名称 |
| 避免扩大事实 | 原试用保留了文档中不同的退役状态；后续复核发现另一现行入口存在相反标签，原试用未完整呈现冲突，这一项不能判为充分通过 |
| 当前与历史分离 | 当前入口指向替代手册；保留历史原文，不全仓改名 |
| 范围与项目兼容 | 发现项目规则与新技能共识不同，记录迁移候选，未自动改造现行体系 |
| 验证限制 | 检查差异范围、新增本地链接、源码路径与操作字段未变；未将静态检查表述为运行或生产验收 |

修订结论：本场景完成了局部入口修正，但对现行来源冲突的处理不充分，也不足以评价任务台账和模板。此前“未暴露通用缺陷”的表述过强。当时运行时包未修改；以下保留提出的优化方案，后续落地情况见文末。

覆盖限制：这是一例当前维护者执行，不能证明跨项目或跨工具效果。尚需验证完整模板产出、任务接续、长文档治理；后续优先选择有明确完成边界的任务表接续场景。

## 试用后的优化方案

本节保留修改提案与验收设计；已执行部分见后续记录，未执行部分不能据此视为完成。项目专属文件清单与原始证据留在项目侧。

| 优先项 | 问题与归属 | 具体修改 | 完成判据 |
|---|---|---|---|
| 1. 当前事实冲突 | 多个现行入口给出不同状态；本轮执行遗漏，现有事实单一来源原则还可澄清处理方式 | 在 SKILL.md 的“定位依据”原条目中补一句冲突处理，避免新增检查表或专用服务规则；候选措辞见下文 | 同时存在两份相反的现行说明时，输出矛盾来源、适用范围与待核实项，不单凭文件新旧或出现次数选择事实 |
| 2. 采纳规则衔接 | 项目仍要求 PRD 跟踪执行进度、台账多处重复更新；属于项目迁移，不是通用模板缺少字段 | 在已授权采纳范围内协调项目指令、规范与模板；新任务使用新规则，旧台账在实际接续时迁移；不批量改历史 | 同一项目不再同时要求两套相反维护方式；历史约定和未迁移文件有清晰边界；不增加新的规则副本 |
| 3. 台账接续验证 | 上轮小修正未使用任务模板，无法证明其可用性 | 选一份有界真实台账，在隔离副本中转换为稳定边界＋唯一任务表；保留有效约束、未完成事项及证据，模拟开始、阻塞与收尾 | 从表中识别可执行项、依赖、阻塞解除条件和结束条件；普通状态变化只更新任务行及日期；取消不冒充完成，范围外问题有去向 |

第 1 项候选措辞（替换式修订原步骤，不新增章节）：

> 定位依据：确认当前需求、相关决策与实现证据，区分事实、推断和未决项。同一事实的现行来源相互冲突时，指出差异及适用范围；无法核实的状态保留未决，不为统一文字而选定一方。

该条仍需用相反现行来源重试，判断原原则是否已经足够、是否确需保留补句；不将服务名、目录或具体退役状态写入技能。

台账试用同时评估一个维护问题：任务及完成条件、当前备注能否保持短而充分。如果必须反复读历史才能接续，先改任务拆分和证据入口，不直接加回 Next / Done / Blocker 摘要。若确有多个任务共享的现场依赖，使用已有可选工作现场区块，不再新增模板字段。

实施顺序：先完成冲突场景复试与单份台账对照，依据实际失败做最小技能修订，再协调项目规范。长文档的正文治理另取有界主题验证；不把本轮入口修正自动扩展为全仓治理。

## 2026-11-10：已知问题收尾与真实台账改造

用户要求案例形成有全局位置的计划，并实际改善项目文档。项目侧建立一份有界案例台账，覆盖入口、简单台账、PRD 与执行依赖、ADR 与实现方案、长指南与历史、取消与证据不足、项目规范收敛；业务状态仍由原业务台账维护。本文件只记录技能评估，不复制该计划的进度表。

- **已修改 skill**：在原“定位依据”步骤补充现行来源冲突的处理，要求说明差异与适用范围、未核实状态保留未决；不新增章节、模板或服务专属规则。
- **冲突场景复查**：实际发现编辑器标签、架构规划与发布实施范围表达不同状态；项目入口现已说明三类依据，未据此宣称生产动作完成。验证的是冲突表达，没有独立生产证据。
- **已修改真实 active 台账**：将一份迁移后的固定三项尾账，从七段正文重整为位置与边界、唯一任务表及必要既有依据；保留三项待办、条件、未分配执行者与历史来源，更新前驱归档的接续指向。不是模板演示副本。
- **项目兼容处理**：根指令与项目规范共同指向同一个试点范围；未转换的台账继续沿用现行格式，避免转换后下一次又被旧规则要求补回重复摘要。
- **接续核对**：任务表可区分无前置依赖的范围核查与有外部条件的功能尾项；能定位下一动作和证据，不能把未排期 / 未启用判为故障或完成。复核实际源码与提交关系，未开展业务实现。
- **技能收敛**：现有任务模板足以承载本例，暂不增加新字段或接续摘要。项目中的代码名称、前缀、服务状态与案例列表不进入运行时包。

覆盖限制：本次完成文档重整与静态接续核对；尚未在后续真实业务推进中验证更新成本，也未进行独立盲测、跨工具或跨项目验证。后续按项目唯一案例台账执行，避免评估记录成为第二套任务进度。

## 2026-11-10：执行者按需与 PRD / 台账职责分离

真实台账评阅中，用户指出大量“待分配”没有实际价值。已修改技能入口、台账规则、最小模板和填写案例：默认省略执行者列，由接续 Agent 在授权范围内推进；指定人或角色就近写在备注，多方分工较多时才加列。真实项目的案例计划及已转换台账同步移除该列，人工确认事项仍明确保留。

随后完成一份真实 PRD 与实施台账的协调：PRD 保留草稿身份、原验收编号与要求、阶段方向和未决设计，移除重复 Progress 与具体执行步骤；实际任务台账维护执行依赖和验证证据，关联台账直接引用约定验收条目的交接任务，不把一个阶段依赖扩大成整个项目阻塞。

源码复核发现旧草稿的数据来源假设已受后续功能影响。处理为更新有证据的现状描述、登记待澄清设计问题，并保留原验收要求等待正式修订；没有为了文档一致而把新方案当作批准结果。该行为由现有“核查关键前提 / 需求与实际行为分开”原则覆盖，无需为本案例再加规则。

验证范围：默认模板无执行者列、人工事项可定位；PRD 原验收条目内容保全；任务及跨台账依赖、链接和技能格式检查。业务未实施，未进行生产验证；当前维护者执行不等于独立盲测。

## 2026-11-11：交付状态复核与 AC 表达

用户指出案例完成与需求交付容易混淆。复核最新远端源码及相邻需求后，将已交付的基础能力与尚未满足的目标验收分开说明；核对实际查询数据源及任务启动入口，不只依据旧接口名称。项目案例计划明确“文档案例完成”不等于业务实现 / 验收 / 发布，撤去无依据的“尚未排期”推断。该问题已由既有证据与状态分离原则覆盖，不增加一套通用状态字段。

按用户反馈补充 AC 写法：行为类优先用 Given / When / Then，技术约束可简写。规则、模板和案例已同步；一份真实 PRD 的身份隔离 AC 作等义展开，其他清楚的技术 AC 保留。检查稳定编号、前提 / 触发 / 可判定结果及原有验收范围，未引入测试框架或新的业务阈值。验证只覆盖文档表达与源码状态核对，未执行功能或生产验收。

# Guide / Runbook 写作与裁剪

新建或重整操作指南时使用 [统一模板](../assets/guide.md)，按需参考 [更新售后联系资料](examples/guide.md)。案例为虚构草稿，不能当作已核实的操作流程；局部编辑沿用既有结构，不为套模板重写全文。

## 文档定位

Guide 回答“怎样完成一件事”；Runbook 强调特定环境下可执行、可核验的操作与恢复。
两者使用同一基础模板，按实际影响裁剪；包括部署运维在内的编号与项目兼容规则，统一见 [文档编号与命名](../SKILL.md#文档编号与命名)。
字段标准、参考手册等既有 Guide 不强制重排为操作手册；本次模板面向操作与排错类文档。

## 最小内容

1. **用途与适用范围**：完成什么、在哪些条件下使用；必要时指出不适用边界。
2. **前置条件**：目标环境、已有权限、依赖与关键参数来源；只写会影响执行的条件。
3. **步骤与结果**：每步操作和可观察结果；发生异常时明确下一步，而非一律继续。
4. **失败处理与恢复**：仅在需要时补充，说明可重复执行性、恢复前提和不能撤销的影响。

不要把实际执行者、勾选进度或每次操作日志放进指南。具体一次执行由台账或已有操作记录承接。

## 如何保持可执行且可信

- 从现有脚本、CLI 帮助、配置或正式契约核实操作方式，不猜命令、参数和服务地址。缺失时明确未核实，不提供看似可直接运行的伪命令。
- 引用实际权威配置或工具入口，不另复制一套容易过期的配置表和实现代码。确需示例时明确与真实值的区别。
- 区分预期结果与真实验证记录。只在读者需要判断适用性时注明已验证版本、环境和证据入口，不为每份指南强制增设验证元数据表。
- 操作完成的判定应对应目标；“构建成功”不能自动替代部署验证，“健康检查通过”不能替代业务验证。
- 恢复必须说明实际可恢复范围。回滚代码不自动撤销数据或外部操作；没有验证过的恢复路径不能承诺一定成功。
- 遵守当前任务与项目已有授权边界；指南本身不授予执行权限，也不额外建立逐步审批流程。

## 维护与裁剪

入口或流程变更时更新对应步骤、预期结果和受影响引用。历史优先引用已有执行记录或 Git；主流程只保留当前有效方法，恢复步骤须按现存资源重新核对，不能沿用已失效的回退前提。
普通指南可只有几个步骤；只有实际存在条件分支时才写故障表，只有需要恢复时才写恢复说明，不凑完整章节。
同一指南覆盖过多独立操作时，按目的拆分并互相链接，不让“常见问题”变成新的知识堆积区。

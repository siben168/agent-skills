# ADR 写作与实现设计

新建或重整 ADR 时使用 [模板](../assets/adr.md)。编号遵循 [文档编号与命名规则](../SKILL.md#文档编号与命名)。删除写作提示，省略不适用章节，沿用项目有效约定。

## 内容与裁剪

- ADR 面向需要长期遵守的职责划分、技术选择或关键取舍；简单实现方案留在 PRD，仅步骤多不构成新建 ADR 的理由。
- 围绕一个连贯的决策主题写清背景与约束、决策与理由、影响与代价、验证要点；短决策可合并章节。备选方案只写真正有意义的选项，不凑数量。
- 新方案标 Draft，只有已确认的决策才作为当前依据；Current 不代表已经实现、验证或上线。
- 复杂方案可增加实现设计章节，说明模块职责、流程与状态、接口/数据归属、失败处理、兼容迁移与恢复边界。已有契约引用其权威来源，不另维护字段表。
- 长度或职责混杂影响理解时，拆为关联附件或独立 ADR；不为拆分新增强制文档类型。

## 设计与执行的分界

| 留在 ADR 的设计 | 留在台账的执行 |
|---|---|
| 消费者兼容新旧字段后，生产者才能切换 | 升级哪个服务、谁执行、是否完成 |
| 迁移失败保留原值，旧格式继续可读 | 运行迁移命令、批次结果与验证记录 |
| 重复请求不能产生第二个任务，用并发请求验证 | 编写和运行具体测试，记录证据 |

必要的技术切换顺序属于设计约束，不展开成排期或任务清单。PRD 维护阶段方向与产品验收，ADR 维护设计不变量和验证方式，两者相互引用；实际测试、分支、提交和发布流水归执行记录。

## 后续维护

同一决策的澄清和兼容细化保留编号；改变核心选择时建立替代 ADR 及替代关系，保留旧决策理由，不能静默抹去历史。
实现完成后保留稳定职责、契约和约束；已经结束且不再适用的迁移过程转入历史记录，正文指明当前结论。
未决事项解决后更新对应决策，不累积审批或对话流水。

需要完整填写示例时，读取 [报表导出采用异步任务](examples/adr.md)。它是虚构草稿，用来说明决策与实现设计如何分节，不是通用架构推荐，也不代表实现或验证已经完成。

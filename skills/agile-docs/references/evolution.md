# 演进与回流规则

## 分清归属

| 新发现 | 保存位置 |
|---|---|
| 项目目录、编号、技术栈、发布方式、组织角色、局部例外 | 该项目约定 |
| 具体问题的过程、证据与失败案例 | 项目复盘，或技能仓库的 Issue、PR、评估材料 |
| 可迁移且能改变 Agent 判断的规则 | 通用 skill 的候选改进 |

不要把项目运行资料、完整复盘或本地路径复制进可分发技能包。
不为每次使用都生成反馈记录；仅在发现实际缺陷或有效改进时记录。

## 进入通用规则的门槛

逐项判断：

1. 去掉项目名、技术栈和特定角色后，规则是否仍成立？
2. 现有原则是否已经覆盖，只是执行不到位？如果是，优先改项目使用方式或澄清原句。
3. 是否可以修改、替换或合并已有规则，而不是新增一个例外？
4. 收益是否足以抵偿所有项目额外的阅读和维护成本？

多个项目出现同类问题可增强依据，但不是自动纳入的理由。证据不足时先保留为候选，不写成全局强制规则。

## 最小回流闭环

具体案例与影响 → 判断归属 → 提出最小规则修订 → 用代表性任务验证 → 通过仓库 PR 评审 → 发布版本。

使用环境没有远程写入能力，或用户仅要求分析时，交付本地提案即可，不自动创建外部消息或发布。
项目记录采用的发布版本或提交，升级时检查规则差异与本地例外；不能用新版本自动覆盖项目约定。

## 验证行为与控制体积

根据改动选择有意义的场景：

- 微小文案/样式修复是否跳过重文档流程。
- 常规需求是否找到并更新已有权威文档，而非重复新建。
- 复杂实现是否放在合适的载体，PRD/ADR 是否避免出现执行任务流水。
- 跨会话接续是否找到当前位置、依赖、下一步及验证限制。
- 范围外问题是否被正确分流，未被悄悄加入本轮。
- 文档冲突、长文档和归档是否保留有效约束与引用。
- 不同项目结构能否直接适配，而非被强制迁移成来源项目的目录。

格式和链接校验不能代替行为验证；跨工具可用性需实际试用，不能仅凭 Markdown 格式宣称验证完成。
每次修订同时检查可删除、合并或下沉的规则；通用入口保持短，条件性细节按需加载。
维护讨论和验证历史放在技能包之外，避免所有使用者都为演进历史支付上下文成本。

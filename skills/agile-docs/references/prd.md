# PRD 写作与裁剪

新建或重整 PRD 时使用 [模板](../assets/prd.md)。编号沿用项目约定，缺省规则见 [技能入口](../SKILL.md#文档编号与命名)。填完删除方括号提示；不适用的章节直接移除，不强制声明 Lite / Standard / Full。

## 内容边界

- 最少写清问题与目标、范围、关键规则和可验证的验收条件。短文可以合并当前结论与目标，不逐条重复正文。
- 元信息按需保留有效性说明、更新日期与关联入口；不默认增加负责人、路径、作者和版本历史表。项目需要维护联系人时可保留，但不把联系人当作任务执行者。
- 产品概要设计用具体流程、行为表或状态图表达；工程需求可用调用场景和契约替代页面设计。不强制用户故事句式或图表。
- 需求规则定义行为，验收标准说明如何证明行为成立。用稳定标识关联，不复制两套同文规则。
- 验收标准描述可观察结果，如“未登录时只显示公开联系方式”，不写成“修改登录判断代码”。默认不使用待办勾选框；项目需要时可记录验收结论与证据链接，不混入开发任务状态。
- 实施阶段说明交付方向和能力边界，单阶段小需求可省略。具体任务、执行者、下一步和执行阻塞放台账；影响需求决策的未决问题仍留在 PRD。
- 简单实现方案放实现备注；复杂设计按主规则链接 ADR 或关联材料。不要逐文件列开发任务。
- 当前有效的需求不等于已实现、已验证或已发布；交付结论只保留必要摘要与证据入口。测试、发布和故障恢复流水留在相应执行记录。
- 按复杂度补充接口、数据、权限、异常、监控、迁移和风险；当长度或职责混杂妨碍理解时拆分，不靠增加摘要掩盖问题。

## AC 写法：条件、触发、结果

行为类验收优先用 Given / When / Then 的思路；可写“给定 / 当 / 则”、一行短句或表格，不要求使用英文关键字、Gherkin 文件或额外测试框架。

- **Given（前提）**：会影响结果的身份、数据状态、环境或配置。只保留区分场景所需条件，不展开测试数据准备过程。
- **When（触发）**：一个主要动作或事件；不要用多步开发任务代替触发。
- **Then（结果）**：可观察、可判定的行为，必要时包括“不应发生”的副作用。避免“正常”“体验良好”“性能提升”等无法直接验收的表述。

技术性不变量、接口约束或兼容性要求可简写为“在某条件下，某结果 / 约束成立”，不为补齐三段编造动作。适用环境、指标和阈值按实际需求给出，不能擅自添加 SLA 或把未决值写成承诺。例如：`AC-2：非法日期范围返回既有参数错误，且不创建导出任务。`

一个 AC 聚焦一个可独立判定的验收目标；相同规则的数据变体可用案例表，独立结果必要时拆分并保留父编号及引用关系。只覆盖有意义的正常、边界和失败条件，不机械枚举组合。测试命令是取证方式，不能单独代替功能验收；格式调整不能改变原有范围或放宽结果。

AC 描述预期，不表示已经通过。实际验证的环境、版本、结果和未覆盖项留在关联任务或报告；需求中的验收结论只引用这些证据。既有 AC 已清晰时不为形式批量重写。

写法参考 [Cucumber 的 Given / When / Then 定义](https://cucumber.io/docs/gherkin/reference/#steps)；这里只借用场景表达，不引入其运行工具依赖。

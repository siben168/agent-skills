# Agile Docs

让人和 Agent 用最少的维护成本找到当前依据、理解设计、推进任务并验证交付。文档应简明、实用、完整、信息一致、逻辑直观。

## 先判断本次需要什么

- 接入项目：识别现有约定与权威入口，只补缺失的必要映射。
- 推进需求：选择文档深度，维护需求、设计、实现和验收之间的关系。
- 恢复或交接任务：读取当前状态与关联依据，核查关键前提，继续下一项工作。
- 治理文档：在指定范围内处理重复、冲突、过期、过长和失效引用。

先读项目指令、文档入口及相关主题摘要，再沿链接检索必要细节。不要默认遍历全部历史资料。
采用已有目录、命名和协作工具；不因使用此 skill 重建文档体系。约定冲突时说明冲突，按当前任务和用户已确认的规则处理；只有影响执行且无法确定的部分才需澄清。

## 文档投入与任务规模相称

- 非常小的 bug、样式和文案调整，可以跳过需求设计与技术方案设计，直接实现并做相应验证。
- 业务规则、接口契约、数据结构、权限或跨模块协作发生实质变化时，先更新相关需求与必要设计。
- 优先更新已有权威文档。确需独立维护的新主题才新建文档。
- 小需求保留目标、范围、关键规则和验收标准；按复杂度补充用户流程、接口、数据、异常、迁移和风险，不机械填满章节。
- 是否创建台账独立判断：跨会话、需要交接或用户要求跟踪时创建；单次能完成的任务通常不建。

新建或重整 PRD 时，读取 [PRD 写作与裁剪](references/prd.md)，其中链接可复制模板和按需案例。普通局部更新沿用现有结构，不为匹配模板重写全文。

## 一个事实，一个权威维护位置

| 内容 | 维护位置与边界 |
|---|---|
| 产品需求 | PRD 维护目标、范围、业务规则和验收标准；只说明实施阶段与方向，不放具体执行任务及任务负责人 |
| 产品概要设计 | 在 PRD 中说明用户流程、页面和业务对象；复杂时拆成关联材料，保持入口明确 |
| 技术架构 | 架构概览说明系统结构，ADR 说明长期决策、理由、备选方案与影响 |
| 技术实现方案 | 简单时放 PRD 实施备注；复杂且涉及架构决策时放对应 ADR 的实现设计章节；没有架构决策时仍可放 PRD 技术方案章节，不制造无意义 ADR |
| 具体执行任务 | 台账维护可完成的任务、执行者、依赖、状态、验证证据和下一步；引用 PRD 的范围和验收条件 |
| 操作知识 | Guide / Runbook 维护当前步骤、前置条件、验证与必要的恢复办法 |

减少文档类型，不等于把所有内容集中到大文件。拆分时按独立职责划分，主文档保留导航，附件各自拥有不同事实。
其他文档可以提供带来源链接的摘要，但不要维护第二套可独立修改的规则、参数或任务状态。
ADR 的长期决策与本次实现设计明确分节；任务勾选、负责人和执行流水留在台账。
新建或重整 ADR 时，读取 [ADR 写作与实现设计](references/adr.md)，其中包含模板与按需案例；局部更新保留现有结构。

## 文档编号与命名

沿用项目已有约定；没有约定时采用以下默认规则：

- PRD、ADR 按类型独立递增：`PRD-001`、`PRD-002`；`ADR-001`、`ADR-002`。编号至少三位，不足补零，超过 999 自然扩展。
- 编号在同一项目的文档体系内唯一，不跨项目统一分配。多服务共用一套项目文档时共用编号空间；独立管理文档的仓库可独立编号，跨仓库引用带仓库名和链接。
- 文件名用 `PRD-001_export_date_validation.md`，标题用 `# PRD-001: 导出日期范围校验`；ADR 同理。编号标识文档，不表示优先级、实施顺序或版本。
- 新建前检查当前文档、草稿与归档，按该类型已使用的最大编号递增；已删除的已知编号也不复用，不填历史空号。多人或多个 Agent 并行创建时，合入前检查重复编号并修正新文档及引用。
- 同一需求或决策的补充、修订保留编号；归档后不重排、不复用。独立的新需求或替代决策使用新编号，并注明替代关系。
- 拆分为独立维护的需求/决策时分配新编号并相互链接；仅为篇幅拆出的附件沿用父文档归属，如 `PRD-001/interaction.md`，不冒充另一份同编号 PRD。
- 正文引用采用带相对链接的编号与名称，减少改名、拆分和归档后的失效引用。其他文档类型及台账按实际需要沿用或建立项目命名，不强制套用 PRD/ADR 编号。

## 需求到交付的最短闭环

1. **定位依据**：确认当前需求、相关决策与实现证据；区分事实、推断和未决项。
2. **明确交付**：记录本轮目标、范围、关键规则与可验证的验收条件；写作深度与风险相称。
3. **实现与验证**：按约定执行，证据注明必要的环境、版本、结果和覆盖限制。实现、验证、发布分别表述，不能相互代替。
4. **同步与收尾**：更新权威内容，沿受影响的引用检查案例、指南、示例和入口；将稳定知识从台账回收到正式文档。

PRD 表达目标行为，代码和运行证据表达实际行为。出现差异时明确差异与原因，不能为了“一致”把缺陷写成需求，或把未经确认的设计写成已实现事实。
需求变更先更新权威范围与验收条件，再调整设计和执行任务；不能事后缩小验收条件来宣称完成。
能从代码、契约或真实示例生成并验证的内容，优先共用来源；检查结果只证明其实际覆盖的范围。

## 台账保持有界且可接续

创建、调整、恢复或关闭台账时，读取 [任务台账规则](references/task-ledgers.md)。核心要求：

- 一个有界目标对应一份活跃台账，创建前查重。
- 展示所属需求与阶段；任务表是执行事实的唯一来源，依赖列不足以表达复杂关系时才补图。
- 具体任务有明确执行者和完成条件。执行者可为人或 Agent，不虚构已分配的责任。
- 新发现的问题先判断归属，不能自动扩张当前范围。
- 从任务状态、依赖与当前备注判断下一步，不默认维护独立接续摘要；推进时就近更新任务行。
- 目标完成后关闭；后续阶段另立并关联，不无限续接。

## 文档长度与生命周期

当前文档、草稿、临时研究和历史资料应易于区分；优先使用项目已有目录与少量状态，不再建立重复的状态总表。
草稿和历史不自动成为实现依据。被采纳的研究结论要进入正式权威文档，正式流程不能仅依赖临时文件。

发现以下现象时，必须指出可读性问题并处理：

- 当前规则与失效方案、历史过程混杂，读者必须自行判断何者有效。
- 一个文件承担多个可以独立维护的职责，检索单一问题需要阅读大量无关内容。
- 正文或台账持续追加，已经妨碍人或 Agent 准确理解与恢复工作。

在本次授权的文档范围内，先删重复与失效内容、提炼当前结论，再按职责拆分并修复导航。只加摘要不能替代正文治理。
只有用户明确同意，才保留影响理解的长文档例外，并简短记录原因。行数可作提示，不用统一硬阈值代替判断。
无关文档的问题应报告并留待专项处理，不借此扩大当前任务。

被替代或不再作为当前依据的内容按项目约定归档，保留原因和替代入口，并更新引用。
完成的需求若仍定义有效行为可以继续作为当前参考；完成不等于过期。拆分或归档前保留仍有效的约束和决策理由。

## 跨项目演进

仅在用户要求改进 skill 或实际使用暴露通用缺陷时，读取 [演进与回流规则](references/evolution.md)。
项目目录、技术栈、发布习惯和局部例外留在当前项目约定；项目问题的案例与证据留在当前项目的复盘、Issue/PR 或评估材料。只有针对 skill 本身的通用改进提案及必要的通用化案例摘要才回流技能仓库。
通用 skill 只保留能改变 Agent 判断的可迁移规则。每次迭代同时检查可删除、合并和下沉的内容。

## 完成本次工作前

按实际改动检查：权威入口清晰、范围未漂移、需求与设计一致、证据没有夸大、受影响链接可达、任务可接续、文档体积可读。
报告修改了什么、验证了什么、哪些内容仍待确认。不要为满足模板而生成空章节或额外文档。
